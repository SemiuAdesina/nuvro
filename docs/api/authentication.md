# Authentication and authorization

Every released product operation requires a verified NUVRO principal. The document-level
security requirement in `contracts/openapi/v1/openapi.yaml` applies to all of them; only
`/health/live` and `/health/ready` opt out with an explicit empty requirement. A contract
test asserts both facts, so a new operation cannot be published unprotected by accident.

## The chain

```
Authorization: Bearer <identity token>
        ↓
Verifier            signature, issuer, audience, expiry
        ↓  user.Identity{Provider, Subject}
Accounts resolver   existing identity, or first-sign-in enrolment
        ↓  user.Principal{UserID, Subject, Provider}
use case            authorization, then work
```

`transport/http/authentication` owns the boundary. `Sessions` composes a `Verifier` with an
`Accounts` resolver and implements `Authenticator`. The OpenAPI security callback rejects a
missing authenticator, a malformed header, an oversized credential, a failed verification or
an incomplete principal, and never returns provider text to the caller. The principal is
placed in the request context; handlers read it with `authentication.From` and never trust a
`userId` in a request body.

## Sign in with Apple

`adapter/external/apple` verifies an identity token against Apple's published keys. It
checks `alg` is RS256, the key id matches a cached JWKS entry, the issuer and audience are
the configured ones, `exp` has not passed and `iat` is not in the future, all with a small
configured leeway, then verifies the RSA signature. Key retrieval is bounded: a five-second
client timeout, a one-megabyte response ceiling, an hour of cache and a one-minute floor
between refreshes, so an unknown key id cannot be used to hammer Apple. A refresh failure
falls back to the cached key rather than failing every request.

Configuration is environment only, so the Apple credentials plug in later with no code
change:

```
NUVRO_APPLE_AUDIENCE        the app's client identifier; required outside development
NUVRO_APPLE_ISSUER          defaults to https://appleid.apple.com
NUVRO_APPLE_KEY_ENDPOINT    defaults to Apple's JWKS endpoint; must be https
NUVRO_APPLE_KEY_TTL         defaults to 1h
```

Until `NUVRO_APPLE_AUDIENCE` is set, no Apple verifier is built. In development the API then
serves health only. Staging and production refuse to start without it.

## Sessions

Apple's identity token expires ten minutes after issue, so it is exchanged once rather than
used as the standing credential. See ADR 0008.

```
POST   /v1/auth/sessions          identity token (+ authorization code)  →  access + refresh
POST   /v1/auth/sessions/refresh  refresh token                            →  rotated pair
DELETE /v1/auth/sessions          bearer access token                     →  session revoked
```

The access token is an HS256 JWT signed with `NUVRO_SESSION_SIGNING_KEY`, carrying the user id
as `sub` and the session id as `jti`, valid for fifteen minutes. Every request checks the
session row and the account status, so revocation is immediate. The refresh token is opaque,
single use and stored as a hash; reuse of a rotated token revokes the entire family. Closing
the account revokes every session the account holds.

`transport/http/authentication.Sessions` tries the session verifier first and falls back to
the identity verifier, so a raw identity token still authenticates for the ten minutes it is
valid. Product handlers cannot tell the difference: both paths produce a `user.Principal`.

## Enrolment

`usecase/account.Resolver` maps a verified identity to an internal account. An unknown
identity is enrolled in one transaction that writes the user, the identity, a default profile
and default preferences. Two concurrent first sign-ins are safe: the unique constraint on
`(provider, provider_subject)` rejects the loser, the adapter maps that to a conflict, and
the resolver re-reads the winner's account instead of failing. Internal identifiers are
UUIDs generated by NUVRO; a provider subject is never used as a user id. A suspended or
deleted account is refused with `forbidden`.

## Development credential

`NUVRO_DEV_AUTH_CREDENTIAL` enables a constant-time credential check that yields a fixed
development identity. It is opt-in, requires at least sixteen characters, and configuration
validation fails startup if it is set while `NUVRO_ENV` is anything other than `development`.
The verifier constructor refuses to build outside development as a second gate. There is no
compiled-in token and no bypass: with nothing configured, the product routes are simply
unreachable.

## Authorization

Authorization is separate and lives in the use cases. Trip reads require membership; a
non-member receives `not_found` rather than `forbidden`, so trip existence does not leak.
Editing requires owner or editor; a viewer receives `forbidden`. Creation takes ownership
from the principal and writes the trip and its owner membership in one transaction, so a
body-supplied owner is ignored. The role check, the read and the write share one transaction
in the update path.
