# NUVRO Android

Native Android application. Kotlin, Jetpack Compose and native Android APIs. No React Native.

## Current state

Architecture only. There are no Gradle files yet.

This is deliberate. No Android toolchain on the machine that scaffolded this repository could
validate a Gradle build, and committing unverified Android Gradle Plugin, Kotlin and Compose
versions would be a guess presented as configuration. The module boundaries and the order of
work are recorded below, and the `android` CI workflow activates itself the moment
`settings.gradle.kts` is committed.

Android follows iOS. The architectural home exists now so that adding it later is not a
repository rewrite.

## Module plan

```
clients/android/
├── app/                      application module, navigation host, DI composition
├── build-logic/convention/   shared Gradle convention plugins
├── core/
│   ├── model/                contract types decoded from the API
│   ├── network/              HTTP transport and error mapping
│   ├── designsystem/         theme, tokens, components
│   ├── localization/         string resources and locale handling
│   └── location/             location authorisation and updates
├── domain/                   client-side use cases and repository abstractions
├── data/                     repository implementations, remote and local data sources
├── feature/
│   ├── onboarding/  discover/  destination/  plan/  travel/  profile/
└── gradle/libs.versions.toml version catalogue
```

Gradle module paths follow the boundary:

```
:app  :core:network  :core:designsystem  :feature:onboarding  :feature:discover
```

Do not split further than this. A module is added when ownership, build performance or
genuine complexity justifies it, not in anticipation.

## Dependency direction

```
feature UI  →  ViewModel  →  domain  →  data  →  core:network
```

- Feature UI renders immutable state and emits events. Unidirectional data flow.
- ViewModels and state holders coordinate client use cases and expose immutable UI state.
- The data layer holds repositories and remote and local data sources.
- The domain layer holds reusable client use cases and repository abstractions.
- Feature modules do not depend on each other.

A Composable never performs an HTTP call, never touches persistence, and never contains
business orchestration.

## What Android must not reimplement

The backend is the authority for:

```
Match Score           destination ranking      budget scoring
itinerary orchestration                        affiliate ranking rules
travel intelligence   entry requirement reasoning
```

Kotlin does not recreate any of it. That is what makes an iOS result and an Android result
identical for the same request.

## Visual direction

Preserve NUVRO brand identity using native Android interaction conventions. Do not attempt to
pixel-copy iOS Liquid Glass; it is an Apple platform behaviour, and imitating it produces
something that feels wrong on Android.

Accessibility is equivalent in outcome, not in implementation: TalkBack, scalable text,
sufficient contrast, adequate touch targets, and a reduced-motion path for the onboarding
artwork.

## Initialising the project

In this order, validating each step before the next:

1. Install the Android SDK and confirm a Gradle build runs on the machine.
2. Create `settings.gradle.kts` with `pluginManagement`, `dependencyResolutionManagement` and
   `rootProject.name = "nuvro"`.
3. Create `gradle/libs.versions.toml` and pin the Android Gradle Plugin, Kotlin and the
   Compose BOM to versions verified against the installed toolchain.
4. Commit the Gradle wrapper generated by that toolchain.
5. Create the root `build.gradle.kts` declaring plugins with `apply false`.
6. Add `build-logic/convention` and the convention plugins that every module applies.
7. Add `app`, then `core:designsystem`, then the first feature module.
8. Include each module in `settings.gradle.kts` only once it has a build file.

The `android` workflow runs `lintDebug` and `testDebugUnitTest` from step 2 onward.
